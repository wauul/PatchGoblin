# PatchGoblin

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Developers and repository maintainers reviewing GitHub Actions failures and missing CI coverage. This audience is inferred from the implemented workflows and the original product brief; no customer research is claimed.

## Product Purpose

Reproduce supported dependency failures, verify bounded repairs or justified pipeline additions in isolation, and open a pull request for human review. Success means readable evidence and a reviewable change, not a green badge without checks.

## Operating Context

GitHub OAuth identity is separate from GitHub App repository authorization. Users select repositories, inspect CI health, launch repair/builder/maintenance jobs, review diagnosis/diffs/command receipts, manage automation and limits, and export or delete account data. The browser extension opens the same workbench.

## Capabilities and Constraints

React 19, TypeScript and Vite; native CSS; Vercel web/API, Groq inference, Neon persistence, Railway worker. Preserve every existing route, API contract, permission check and destructive-action confirmation. No automatic merges, new job submissions for visual testing, payments or invented proof. Python pip/uv and bounded Node workflows are supported with documented limitations. Organization/private and native extension execution are not live-verified.

## Brand Commitments

Preserve the PatchGoblin name and existing SVG mascot. The user requests a replacement visual world across marketing, product, documentation and extension surfaces, complete light/dark themes and deliberate mobile layouts. Direction selection and ordinary implementation decisions are explicitly delegated. No decorative punctuation on names or routine labels, fake testimonials, claims or statistics.

## Evidence on Hand

README.md, docs/product-verification.md and docs/product-results.json contain actual public-lab evidence, including failed trials. Public example PRs include dependency repair #4/#6, CI creation #1 in the product lab, and maintenance #5. The independently evaluated historical result is 11/12, not a current Groq success guarantee. Existing screenshots document incumbent interfaces.

## Product Principles

- Evidence before submission.
- Repository access must remain explicit.
- Review stays with the maintainer.
- Describe failures and limitations precisely.
- Use calm, scannable task interfaces with a recognizable brand.

## Accessibility & Inclusion

The redesign must preserve keyboard and screen-reader semantics, visible focus, accessible feedback, reduced motion, text resizing, touch targets and narrow-screen usability. Respect system appearance with a persistent user override.
